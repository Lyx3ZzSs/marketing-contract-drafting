## 2026-10-23：间歇性登录 401 根因与修复

真实浏览器复现：同一 SSO 会话首次加载成功，第二次重新走授权回调失败。
API 于 `2026-10-23T01:58:52.995623Z` 记录 `ImmatureSignatureError`：

- 签发时间 `iat = 1792720733`；记录诊断时 API 时钟 `1792720732.995425`。
- 过期时间 `exp = 1792721633`，距离当时约 900 秒，实际未过期。
- 失败请求标识 `1370c07676e9434581d4a339569fe7e6`。
- 保持页面内同一登录会话，不重新授权，稍后请求 `/auth/me` 返回 200。

证据表明新令牌签发时间略超前于 API 验证时钟；PyJWT 默认零容差将其判为尚未生效。
诊断记录与 iat 差约 4.6 毫秒，不等于两台主机的精确时钟差（还含请求和日志时延）。
旧代码把所有 JWT 校验异常统一显示为“登录已失效”，掩盖了真正原因。
未检查或修改认证服务器的系统时钟/NTP 配置，因此不推断其时钟漂移的基础设施原因。

修复：使用 PyJWT `leeway`，由 `OIDC_CLOCK_SKEW_SECONDS` 配置，默认 5 秒、限定 0–30 秒；
对 iat、nbf、exp 统一容差，仍验证 RS256 签名、issuer、audience 与角色。
真正过期、时间差超限、其他无效凭据分别显示对应提示。
持久日志仅包含异常类型和请求标识，不保存凭据、身份信息或临时解码数据。
认证平台与 API 宿主机仍应保持时间同步。

验证：先新增固定时钟回归测试，修复前 2 项容差用例失败；修复后全部通过。
覆盖 1 秒/5 秒超前可接受，6 秒超前和超出容差的过期令牌拒绝；
另验证错误提示区分、日志请求关联和不记录 Token。
后端非集成测试 103 项通过，Ruff、格式检查、Mypy 通过。
重建并启动 API 后，真实浏览器连续 20 次重新走授权回调全部进入系统。

参考：[PyJWT 校验 API](https://pyjwt.readthedocs.io/en/stable/api.html)。
