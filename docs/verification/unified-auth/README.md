## 2026-10-23：间歇性登录 401 根因与修复

真实浏览器复现：同一 SSO 会话首次加载成功，第二次重新走授权回调失败。
API 于 `2026-10-23T01:58:52.995623Z` 记录 `ImmatureSignatureError`：

- 签发时间 `iat = 1792720733`；记录诊断时 API 时钟 `1792720732.995425`。
- 过期时间 `exp = 1792721633`，距离当时约 900 秒，实际未过期。
- 失败请求标识 `1370c07676e9434581d4a339569fe7e6`。
- 保持页面内同一登录会话，不重新授权，稍后请求 `/auth/me` 返回 200。

证据表明新令牌签发时间略超前于 API 验证时钟；PyJWT 默认零容差将其判为尚未生效。
诊断记录与 iat 差约 4.6 毫秒，不等于两台主机的精确时钟差（还含请求和日志时延）。
旧代码把所有 JWT 校验异常统一显示为“登录已失效”，掩盖了真正原因。
未检查或修改认证服务器的系统时钟/NTP 配置，因此不推断其时钟漂移的基础设施原因。

修复：使用 PyJWT `leeway`，由 `OIDC_CLOCK_SKEW_SECONDS` 配置，默认 5 秒、限定 0–30 秒；
对 iat、nbf、exp 统一容差，仍验证 RS256 签名、issuer、audience 与角色。
真正过期、时间差超限、其他无效凭据分别显示对应提示。
持久日志仅包含异常类型和请求标识，不保存凭据、身份信息或临时解码数据。
认证平台与 API 宿主机仍应保持时间同步。

验证：先新增固定时钟回归测试，修复前 2 项容差用例失败；修复后全部通过。
覆盖 1 秒/5 秒超前可接受，6 秒超前和超出容差的过期令牌拒绝；
另验证错误提示区分、日志请求关联和不记录 Token。
后端非集成测试 103 项通过，Ruff、格式检查、Mypy 通过。
重建并启动 API 后，真实浏览器连续 20 次重新走授权回调全部进入系统。

参考：[PyJWT 校验 API](https://pyjwt.readthedocs.io/en/stable/api.html)。


## 2026-11-02：刷新后再次验证登录的诊断

用户反馈在登录后的主界面刷新会反复出现验证登录。使用临时跨页面事件记录核对；记录仅含时间、事件名、pathname、顶层/iframe 和有效期秒数，不包含账号、Token、授权码或查询参数。诊断脚本和认证模块中的探针已从源代码移除，认证行为未修改。

用户本次复现记录（北京时间）：

| 事件 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 主界面文档启动，navigation.type=reload | 16:59:54.109 | 16:59:56.767 |
| 自动发起认证 | 16:59:54.290 | 16:59:56.881 |
| 回调取得令牌，剩余有效期 900 秒 | 16:59:54.557 | 16:59:57.082 |
| 账号校验成功，HTTP 200 | 16:59:54.605 | 16:59:57.100 |

第一轮校验成功后约 2.1 秒，主界面再次卸载，然后以 reload 类型启动第二轮。两轮之间未记录到 expire-session、silent-renew-error、token-expired、api-401、Vite full-reload/update 或 WebSocket close。证据见 `refresh-navigation-events.json`。

已确认的应用层原因：`auth.ts` 每次创建新的 InMemoryWebStorage，页面重载后 session 和 identity 同时丢失；initializeAuth 仅创建客户端，没有恢复用户会话的步骤；路由守卫把缺少 identity 的访问导向 /login，SignIn 挂载后自动 signinRedirect。因此每次整页重载都要走 / → /login → 认证平台 → /callback → / 的完整流程，即使 SSO 会话和令牌本来仍有效。用当前安装的 oidc-client-ts 实例验证同一模拟存储键：重载前存在，创建新的内存 store 后不存在。

本次证据不支持把连续认证归因于 401 或新令牌立即过期。navigation.type=reload 本身不能区分浏览器按钮、快捷键、扩展或页面脚本发起的重载；没有捕获到第二次重载的调用来源，不能据此指认浏览器扩展，也不能宣布完整循环根因已经定位。当前读取了扩展列表，未禁用或修改任何扩展。

后续修复目标应分开验收：有效应用会话在刷新后能够恢复，避免正常刷新重走顶层 SSO；认证退出/重试有幂等与循环保护；如果确实存在非预期的第二次文档重载，仍需捕获其发起来源。当前内存 Token 策略见前文，改变会话存储方案需要单独设计，不能通过仅隐藏验证提示解决。


## 2026-11-02：刷新恢复会话与防循环修复

按用户授权修复已确认的应用侧原因。当前策略取代前文“Token 仅在内存”的历史实现：OIDC 用户会话使用当前标签页的 sessionStorage，刷新后通过 getUser 恢复；/callback 单独处理本轮授权事务，避免先恢复旧账号。有效会话仍需 /auth/me 成功后才能进入业务界面，权限不从缓存直接放行。网络/身份服务临时失败保留可恢复会话并显示错误；损坏的会话清理后提示手动登录。

临近过期或过期的会话先续期。后台定时续期与 API 请求续期使用同一 Promise，关闭库的独立自动续期，避免两条通道同时使用轮换的 Refresh Token。401 和续期失败只执行一次清理及整页跳转；登录页读取失效状态后停止自动认证，提供“重新登录”。自动登录尝试在 60 秒内未完成时阻止重复跳转，显式重试可继续。退出后迟到的续期响应会再次移除其写入的会话，迟到的 401 不再覆盖退出跳转。

验证：

- 修复前新增 3 项针对性回归失败：恢复后 identity 为空、存储无法跨刷新保留、并发 401 跳转两次。修复后认证模块 18 项、登录界面 4 项通过。
- 全部前端测试 69 项通过，ESLint、TypeScript 和 Vite 生产构建通过。
- 实际已登录 Chrome 刷新后，Performance Navigation 的加载路径及当前路径均为 `/`；认证资源只有 `/api/v1/auth/config` 和 `/api/v1/auth/me`，页面保持登录，没有再次加载 /callback 或认证平台端点，见 `refresh-browser-proof.json`。
